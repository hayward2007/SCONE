# PPO 진단과 개선 계획 (2026-09-01)

대상: `src/rl/walk_learn.py`, `src/assets/model.xml`
증상: (1) 전진 시 뒤쪽 두 다리가 기여하지 않음 (2) 좌우 비대칭 (3) 왼쪽으로 편향
(4) 최대 속도가 낮음

검증 방법: `model.xml`을 MuJoCo 3.12로 직접 로드해 관절 축·자세·질량중심을 수치로
계산했다. 아래 "검증됨" 표시는 추정이 아니라 계산 결과다.

## 0. 먼저 배제한 것 (검증 결과 문제 없음)

### 기구 모델은 좌우 대칭이다 — 검증됨
몸체 좌표계에서 9개 좌우 관절 쌍의 회전축을 모두 비교했다. 거울면은 몸체 $xz$
평면($y\to-y$)이고, 축벡터(pseudovector) 거울상 판정 $(a_x,a_y,a_z)\to(-a_x,a_y,-a_z)$
에 대해 **9쌍 전부 MIRROR-OK**였다.

```
M01[-0,-0,-1] vs M02[-0,-0, 1]   MIRROR-OK      (몸체 관절)
M07[-.707,-.707,0] vs M08[.707,-.707,0]  MIRROR-OK  (중간 관절)
M13[.707,.707,-0] vs M14[-.707,.707,-0]  MIRROR-OK  (말단 호)
... 9/9 통과
```

`degrees_to_raw`는 모터 ID를 무시하므로(`controller.py:250`, `del motor_id`) 좌우에
**같은 각도를 주면 정확히 거울 자세가 나온다.** SPORT 스탠스에서 실제 접촉 중심을
비교하면 좌우 오차는 x 1.1 mm, y 1.2 mm, z 3.4 mm로 CAD 반올림 수준이다.

→ **비대칭은 기구가 아니라 학습 쪽 문제다.**

### 보상의 속도 측정점은 올바르다 — 검증됨
`root_body` 프레임 원점이 로봇 질량중심에서 평면상 0.157 m 떨어져 있어 처음에는
`mj_objectVelocity`가 코너 점의 속도를 보고할 것으로 의심했다. 수치로 확인한 결과
이 함수는 **질량중심 속도를 반환**한다(질량중심을 고정하고 yaw 0.5 rad/s를 주면
보고값 0.0005 m/s, 프레임 원점을 고정하면 0.0787 m/s). 문제 없음.

## 1. 즉시 확인할 것 — 학습과 재생의 기준 궤적이 다르다

`walk_learn.py:1475`

```python
def _resolve_reference_motion(command_name, selected):
    if selected is not None: return normalize_reference_motion(selected)
    if command_name == "enjoy": return "hardcoded"      # 재생 기본값
    return "tripod-gait"                                # 학습 기본값
```

policy는 `tripod-gait`(IK 기반 삼각보) 위에 residual을 얹도록 학습되는데, `enjoy`는
기본적으로 `hardcoded`(관절공간 사인파) 위에 그 residual을 더한다. **residual이
학습한 적 없는 base motion에 더해지고 있다.**

관측되는 증상 대부분이 이것만으로 설명될 수 있다. 재학습 없이 지금 바로 확인 가능:

```bash
python -m src.rl enjoy --reference-motion tripod-gait ...   # 학습과 동일 기준
python -m src.rl enjoy --reference-motion hardcoded   ...   # 현재 기본값
```

두 결과가 다르면 "학습 실패"가 아니라 재생 설정 문제다. **다른 어떤 수정보다 먼저
이것을 확인할 것.**

## 2. 최대 속도가 낮은 이유 — 명령이 기준 궤적의 6배다

학습용 `tripod-gait` 기준 궤적 설정 (`walk_learn.py:353`):

| 항목 | 값 |
| --- | --- |
| `cycle_frequency` $f$ | 0.7 Hz (명령과 무관하게 고정) |
| `max_stride` $s^{\max}$ | 0.060 m |
| `duty_factor` $D$ | 0.5 (`GaitConfig` 기본값) |

스트로크는 $s=Du/f$이고 $s\le s^{\max}$이므로 기준 궤적이 낼 수 있는 속도 상한은

$$u_{\max}=\frac{s^{\max}f}{D}=\frac{0.060\times0.7}{0.5}=\mathbf{0.084\ m/s}$$

그런데 명령 범위는 `CURRICULUM_RANGES`에서 easy 0.30, medium 0.40, full 0.50 m/s다.
**명령이 기준 궤적 능력의 3.6~6배다.**

속도 보상은 $\exp(-\|e\|^2/\sigma^2)$, $\sigma=0.25$이므로

| 명령 | 도달 가능 | 오차 | 속도 보상 |
| ---: | ---: | ---: | ---: |
| 0.30 m/s | ~0.084 | 0.216 | 0.47 |
| 0.50 m/s | ~0.084 | 0.416 | **0.06** |

residual($\pm10/12/15^\circ$)이 스트로크를 대략 배로 늘려도 0.15~0.20 m/s가 한계다.
즉 **고속 구간에는 gradient가 사실상 없다.** 정책은 속도를 포기하고 자세·행동
패널티만 최적화하는 것이 이득이며, 이는 "느리고 소극적인 보행"으로 나타난다.

`_advance_phase`는 모델 기준 궤적이 있으면 즉시 return하므로(`walk_learn.py:517`)
주파수가 명령에 따라 올라가지도 않는다.

## 3. 뒤쪽 다리가 기여하지 않는 이유 — 보상에 그럴 이유가 없다

세 가지가 겹친다.

1. **관측에 접촉 정보가 전혀 없다.** 70차원 관측은 몸체 속도/자세, 관절 위치·속도,
   이전 행동, 명령, 위상·헤딩 sin/cos뿐이다(`walk_learn.py:676`). 정책은 어떤 다리가
   지면에 닿아 있는지 **알 수 없다.**
2. **보상에 다리 기여 항이 없다.** 부하 분담, 접촉 스케줄, air-time, 발 clearance
   어느 것도 없다. `stance_contacts`는 진단 출력일 뿐 보상에 들어가지 않는다.
3. **행동 크기 패널티가 균등하다.** `action_magnitude_weight=0.25`가
   $\mathrm{mean}(a^2)$를 18관절 균등으로 벌한다. 어떤 다리를 쓰든 보상은 몸체
   속도 하나로만 측정되므로, **기여가 애매한 다리의 residual을 0으로 두는 것이
   엄밀히 최적**이다. 지금 보이는 현상은 학습 실패가 아니라 이 보상의 정확한 해다.

부수적으로, 몸체 좌표계에서 다리 힙 위치는 x = −0.005 / +0.125 / +0.255 이고
질량중심은 x = +0.124 로 정확히 가운데 쌍 위에 있다. 앞뒤 발자국은 질량중심 기준
∓0.33 m로 대칭이므로 **기하학적으로는 앞뒤 어느 쌍도 불리하지 않다.**

> 확인 필요: 몸체 +x가 전방인지 후방인지. 내부 탑재물 주석은 "front-to-rear" 순서로
> L1/L2 배터리(x=−0.005) → RPi → L3/L4 배터리(x=+0.125)를 배치한다고 적혀 있어
> **전방이 −x**임을 시사한다. 반면 RL과 gait 코드는 +x를 전진으로 사용한다. 이것이
> 뒤집혀 있으면 사용자가 "뒷다리"라고 부르는 쌍이 실제로는 선행 다리다.

## 4. 좌우 비대칭과 왼쪽 편향

기구가 대칭임을 확인했으므로 원인은 학습 설정에 있다.

### 4.1 대칭성을 강제하는 장치가 하나도 없다
미러 데이터 증강도, 대칭 손실도, 좌우 균형 보상도 없다. 좌우가 완전히 독립적인
파라미터로 학습되므로 PPO가 대칭해로 수렴할 이유가 없다.

### 4.2 초기 상태·도메인 랜덤화가 전무하다
`reset()`에서 랜덤화되는 것은 **보행 위상 하나뿐**이다(`walk_learn.py:958`).
초기 관절 섭동, 몸체 자세/헤딩 랜덤화, 외란 push, 질량·마찰·지연 랜덤화,
관측 노이즈가 전부 없다. 매 에피소드가 동일한 상태에서 시작하므로 한쪽으로 치우친
해가 한 번 형성되면 그것을 깨뜨릴 압력이 없다.

### 4.3 헤딩 보상이 너무 헐겁다
`heading_error_sigma = 0.60 rad = 34.4°`, `heading_weight = 0.75`.
20° 정상편차의 보상은 $\exp(-(0.35/0.6)^2)=0.71$로 거의 무료다. 게다가 yaw 항은
**각속도** 추종만 벌하므로 누적 헤딩 오차에 대한 복원력이 약하다. easy 커리큘럼은
yaw 명령이 0이라 헤딩 유지가 유일한 방향 신호인데 그 신호가 34° 폭으로 뭉개져 있다.

### 4.4 미러 증강에 필요한 사상 (검증된 대칭성 기반)
관절 축이 정확한 축벡터 거울상이고 각도 변환에 부호가 없으므로, 미러 사상은
**부호 없는 단순 치환**이다: 다리 $1\leftrightarrow2,\ 3\leftrightarrow4,\ 5\leftrightarrow6$,
즉 모터 ID $i\leftrightarrow i\pm1$ (각 6개 군 내부에서).

삼각보가 $\mathcal{T}_A=\{1,4,5\}$, $\mathcal{T}_B=\{2,3,6\}$이므로 이 치환은
**두 삼각보를 맞바꾼다.** 따라서 위상도 반주기 이동해야 한다.

70차원 관측에 대한 미러 연산자 $M$:

| 구간 | 내용 | 변환 |
| --- | --- | --- |
| `[0:3]` | 선속도 (극벡터) | $(+,-,+)$ |
| `[3:6]` | 각속도 (축벡터) | $(-,+,-)$ |
| `[6:9]` | 투영 중력 (극벡터) | $(+,-,+)$ |
| `[9:27]` | 관절 위치 | 치환 $P$ |
| `[27:45]` | 관절 속도 | 치환 $P$ |
| `[45:63]` | 이전 행동 | 치환 $P$ |
| `[63:66]` | 명령 $(v_x,v_y,\omega_z)$ | $(+,-,-)$ |
| `[66:68]` | $(\sin2\pi\phi,\cos2\pi\phi)$ | $(-,-)$ — 반주기 이동 |
| `[68:70]` | $(\sin e_\psi,\cos e_\psi)$ | $(-,+)$ |

행동(18차원)은 치환 $P$. 이 $M$으로 rollout을 복제해 배치에 추가하면 대칭성이
데이터 수준에서 강제된다.

## 6. 개선 계획 (우선순위)

### P0 — 재학습 없이 오늘 확인 (반나절)
1. **`enjoy`의 기준 궤적을 `tripod-gait`로 맞춰 재생.** 증상이 사라지는지 확인
   (§1). 사라지면 나머지 진단의 우선순위가 완전히 바뀐다.
2. **다리별 진단 로그**: 전진 명령에서 다리 1..6 각각의 접촉 시간 비율, 수직
   임펄스, 발 전후 변위 진폭을 기록. "뒷다리가 논다"를 정량화하고, 몸체 +x가
   전방인지도 이 로그로 확정된다.

### P1 — 속도 상한 해제 (재학습 필요, 설정만 수정)
3. **기준 궤적을 명령 범위에 맞춘다.** 둘 중 하나:
   - $f$와 $s^{\max}$ 상향: 예 $f=1.2\,$Hz, $s^{\max}=0.12\,$m → $u_{\max}=0.29\,$m/s
   - 또는 명령 범위를 기준 능력에 맞춰 하향(easy 0.10, full 0.20)
   지금처럼 6배 벌어진 상태로는 어떤 하이퍼파라미터도 소용없다.
4. **기준 주파수를 명령에 연동.** 모델 기준 궤적을 쓸 때도 활성도에 따라
   `cycle_frequency`를 올린다(현재 `_advance_phase`가 즉시 return).
5. **속도 커리큘럼**: 성공률에 따라 명령 상한을 점진 확대.

### P2 — 대칭성 (재학습 필요)
6. **§4.4의 미러 증강**을 rollout 버퍼에 적용. 가장 확실하고 비용이 낮다.
7. **초기 상태 랜덤화**: 관절 ±5°, 몸체 yaw 전 범위, 높이 ±1 cm, 초기 속도 소량.
8. **외란 push**: 1~3초마다 몸체에 임의 방향 임펄스.
9. **헤딩 보상 강화**: `heading_error_sigma` 0.60 → 0.15~0.25, 필요하면 헤딩 오차
   적분 항 추가.

### P3 — 뒷다리 참여와 효율
10. **관측에 접촉 정보 추가**: 6개 발의 접촉 불리언 + 정규화 수직력(12차원 추가,
    70 → 82). 정책이 다리 상태를 볼 수 없으면 다리 역할을 배울 수 없다.
11. **접촉 스케줄 보상**: 삼각보 위상과 실제 접촉의 일치도, 또는 air-time 보상
    (스윙 시간이 목표 구간에 들 때 +). 다리별로 주면 놀고 있는 다리가 직접 벌점.
12. **부하 분담 항**: 여섯 다리 수직 임펄스 분포의 균등도(엔트로피 또는 분산 벌점).
13. **`action_magnitude_weight` 재설계**: 균등 $\mathrm{mean}(a^2)$ 대신 실제
    전류/토크 기반 비용으로 교체하거나 0.25 → 0.05로 낮춘다. 현재 값은 "다리를
    쓰지 않는 것"에 직접 보상을 준다.

### P4 — 학습 규모
14. `num_envs` 4 → 64 이상(가능하면 수백), `total_timesteps` 1e6 → 5e7 이상.
15. `gamma` 0.99 → 0.995 (지평 4 s), 또는 `episode_seconds` 연장.

## 7. 실행 순서 제안

```
P0-1 재생 기준 통일 확인          ← 여기서 결론이 크게 바뀔 수 있음
  └ 증상 지속 시:
      P1-3 기준 궤적 속도 상한 수정  ← 속도 문제의 유일한 근본 원인
      P2-6 미러 증강                 ← 비대칭의 가장 저렴한 해결
      P3-10/11 접촉 관측 + 스케줄 보상 ← 뒷다리 참여의 유일한 직접 처방
      P4  규모 확대
```

P1-3과 P3-13은 서로 반대 방향으로 작용하므로 함께 바꿔야 한다. 속도 상한을 풀면서
행동 패널티를 그대로 두면 정책은 다시 "가만히 있기"로 수렴한다.
